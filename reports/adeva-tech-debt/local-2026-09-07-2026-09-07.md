### 🟡 Planificar

#### Dependencia `axios` con múltiples CVEs activos (SSRF, bypass de autenticación, DoS)

**Módulo:** `src/http/index.ts` (único punto de instanciación del cliente HTTP; consumido por los 4 módulos de `src/services`)
**Smell:** Dependencia de producción con vulnerabilidades conocidas sin parchear
**Fuente:** `npm audit --omit=dev` — severidad original: **Alto** (rango vulnerable reportado 1.0.0–1.17.0 cubre la versión instalada 1.6.2); incluye además `form-data` (transitiva vía axios, severidad **Crítica**) y `follow-redirects` (transitiva vía axios, **Moderada**), ambas resueltas por el mismo fix
**Criticidad del módulo:** Observada — `src/http/index.ts` es el cliente HTTP único de toda la aplicación (arquitectura declarada en `SYSTEM_CONTEXT.md > Arquitectura`); cualquier CVE ahí tiene el blast radius máximo del proyecto
**Calor:** Tibio (sin historial de PRs verificable; se trató en esta misma sesión solo para agregar JSDoc, sin tocar la versión de la dependencia)
**Esfuerzo estimado:** Bajo — actualizar `axios` dentro del mismo major (`^1.6.2` → `^1.20.0`) vía `npm audit fix`; sin cambios reportados como breaking para las 3 vulnerabilidades de producción
**Impacto:** aunque el proyecto es de referencia/educativo y no tiene backend real conectado (`baseURL` sin configurar, todo corre contra `axios-mock-adapter`), la superficie de exposición real hoy es baja — pero el fix es trivial y elimina de una vez SSRF, bypass de auth vía prototype pollution y DoS en la única librería HTTP del proyecto, quedando listo para el día que se conecte una API real.
**Acción recomendada:** correr `npm audit fix` (sin `--force`) para actualizar `axios`, `form-data` y `follow-redirects` a las versiones parchadas dentro del rango semver declarado; correr `npm run test` y `npm run type-check` después para confirmar que no rompe nada (los 88 tests actuales cubren `src/http` y los 4 servicios que dependen de axios).

### Addendum — 2026-09-07 (post-remediación)

Al aplicar los ajustes de este reporte se ejecutó `npm audit fix` (sin `--force`), lo cual **resolvió** el ítem 🟡 (`axios`/`form-data`/`follow-redirects`) y el ítem 🟢 de `nanoid`/`postcss`/`svgo` — ambos dentro de los rangos semver ya declarados en `package.json`, sin cambios de código, verificado con `npx vitest run` (91/91 ✅) y `vue-tsc --noEmit` (0 errores). También se cerró el ítem 🟢 de ramas de error sin cubrir en `stores/deal.ts` y `stores/product.ts` (cobertura de esas capas ahora 100% en statements/branches/funcs/lines).

**Corrección al alcance original de este reporte:** el análisis de `npm audit` original solo cubrió `--omit=dev` (dependencias de producción). Al correr `npm audit fix` se reveló que también hay CVEs de severidad **crítica** y **alta** en devDependencies que no estaban en el reporte original:
- `happy-dom` (crítica — RCE vía `<script>`, escape de VM context)
- `vitest` (crítica — lectura/ejecución arbitraria de archivos cuando el UI server está activo)
- `esbuild`/`vite` (moderada — cualquier sitio web puede leer respuestas del dev server)
- `vue-template-compiler`/`vue-tsc` (moderada — XSS)

Los cuatro requieren `npm audit fix --force` (bumps mayores: `vite`→8.2.2, `happy-dom`→20.14.0, `vitest`→5.0.0), consistentes con el ítem 🟢 ya documentado sobre el árbol de dependencias desactualizado (Esfuerzo Alto). Exposición real: estas herramientas solo corren en desarrollo/testing local, nunca en el bundle de producción — no se eleva su tier por esto, pero se deja registrado para que la próxima corrida de `adeva-tech-debt` las evalúe formalmente en su propio ítem (hoy solo estaban mencionadas de forma agregada en el ítem sistémico de dependencias desactualizadas, sin desglosar severidad de CVE).
